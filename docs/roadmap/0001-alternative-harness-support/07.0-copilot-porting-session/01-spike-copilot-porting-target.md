# 01 - Spike: Copilot's own agent/skill config convention

**Parent task:** 07.0 Copilot porting session
**State:** ✅ Complete (2026-08-30)
**Depends on:** task 02.0 (Copilot's confirmed non-interactive/tool-allowlist
contract - this spike is narrower, just the output-location question)
**Blocks:** 02 (this task)

## Objective

Determine where GitHub Copilot's own tooling conventionally expects
repository-level agent/skill/instruction configuration to live, so
`port.py`'s prompt can name a concrete target instead of a generic "wherever
is idiomatic for you" sentence. This is research, not implementation - no
source file changes.

## Questions to answer

1. Does Copilot have an established, documented convention for
   repository-scoped custom instructions or agent-like configuration (for
   example, a well-known file or directory GitHub's own docs point at)?
2. If yes: is it a single file, a directory of files, or something more
   structured (front-matter, JSON/YAML config)? Record enough shape detail
   that a prompt sentence naming it would actually help Copilot, not just
   gesture at it.
3. Does writing to that location require any tool-allowlist entry beyond what
   task 02.0's confirmed contract already grants for the marker-research use
   case (`Read`/`Grep`/`Glob`/`Edit`/`TodoWrite`)? Porting needs `Write`
   (task 06.0 subtask 01's `PORTING_TOOLS`) to a path that, unlike marker
   research, is NOT under `.claude/` - confirm Copilot's tool-allowlist syntax
   permits scoping `Write` to (or excluding it from) specific paths if that
   matters for safety, or whether it's an all-or-nothing grant.
4. Is there a meaningful difference between "agent" and "skill" equivalents in
   Copilot's own model, or does it use a single flatter concept for both?
   (This affects only the wording of the hint, not this codebase's structure -
   Claude's four-kind split stays canonical regardless of the answer.)

## Constraints

- Confirm against GitHub's current, published documentation - this is a
  fast-moving product area; re-verify rather than relying on possibly-stale
  general knowledge.
- If no fixed convention exists, that is a legitimate answer - record it and
  let `porting_target_hint` stay `None` (task 01.0 subtask 01's default).

## Success criteria

- [x] This file records a dated, sourced answer to all four questions, or an
      explicit "no fixed convention, hint stays generic" conclusion.
- [x] `status.md` reflects the spike's outcome before subtask 02 starts.

## Findings (2026-08-30)

Confirmed against the installed `copilot` CLI (`GitHub Copilot CLI 1.0.81`) via `copilot skill
--help`, `copilot plugin --help`, `copilot init --help`, and `copilot --help`'s own flag
descriptions (`--add-dir`, `--agent`, `--no-custom-instructions`), which cite GitHub's published
docs URLs directly (`docs.github.com/copilot/...`).

**Q1. Established, documented conventions - yes, several, all confirmed:**
- **Repo-wide instructions:** `.github/copilot-instructions.md`, generated by `copilot init`
  ("Analyzes your codebase ... and generates a `.github/copilot-instructions.md` file with
  contextual guidance"). Docs: `docs.github.com/copilot/how-tos/configure-custom-instructions/
  add-repository-instructions`.
- **Custom instructions (broader):** loaded automatically from `AGENTS.md` and "related files"
  unless `--no-custom-instructions` is passed - this is the same `AGENTS.md` convention this
  repo's own root already has (see root `CLAUDE.md`'s "the root `AGENTS.md` is a near-duplicate
  of an older revision of this file").
- **Skills:** `copilot skill --help`'s own text is explicit and unambiguous: "Skills are reusable
  instructions (`SKILL.md` files) ... discovered from: Project `.github/skills/`,
  `.agents/skills/`, or **`.claude/skills/`**" (project-scoped, no flag needed) plus
  `~/.copilot/skills/` or `~/.agents/skills/` (personal-scoped). Notably, Copilot already
  auto-discovers skills directly from `.claude/skills/` - a real, confirmed overlap with this
  milestone's own source format, worth naming in the porting hint.
- **Agents:** confirmed via `--add-dir`'s help text - "load its `.github/skills` and
  `.github/agents` as trusted configuration" - so `.github/agents/` is the parallel
  project-scoped agent location. **Caveat, disclosed not guessed:** `--help` text confirms this
  discovery explicitly for a directory added via `--add-dir` (i.e., a directory *other than* the
  session's own cwd); whether `.github/agents/` under the cwd itself is auto-discovered the same
  way project skills are was **not independently confirmed** in this pass (plausible by symmetry
  with the skills convention, but not verified against `--help` text or docs the way skills was).
- **Plugins** (`copilot plugin --help`) can bundle "additional skills, agents, hooks, MCP servers,
  and LSP servers" - so a "hooks" *concept* exists in Copilot, but only as something a plugin
  packages, not as a bare project-level directory Copilot scans the way it does `.github/skills/`
  or `.github/agents/`. **No project-level hooks-directory convention was found or is claimed.**
  Similarly, no dedicated "loops" concept (a saved recurring/orchestrated command sequence) was
  found anywhere in `--help` or the topics list (`config`, `commands`, `limits`, `environment`,
  `logging`, `monitoring`, `permissions`, `providers`, `billing`, `sandbox` - no `agents` or
  `loops` topic exists; `copilot help agents` returns "Unknown help topic").

**Q2. Shape:**
- Skills: one `SKILL.md` file per skill, inside a directory under one of the confirmed skill
  locations (this is literally the same `SKILL.md`-per-directory shape `catalog.py`'s own
  `discover` already expects for Claude's `skills` kind - see `src/awesome_templates/CLAUDE.md`'s
  catalog.py entry: "`skills` entities are directories containing a `SKILL.md`").
- Agents: a directory (`.github/agents/`), file-level shape not further detailed by `--help`
  text available in this pass - not guessed, left as an open detail for the porting session's own
  prompt to leave to Copilot's judgment (matching this milestone's own porting-rules stance:
  "read the Claude-authored file ... re-author using whatever shape is idiomatic for you").
- Repo instructions: a single Markdown file (`.github/copilot-instructions.md`), prose, not
  front-matter/structured.
- No hooks or loops shape exists to describe (see Q1).

**Q3. Additional tool-allowlist needed for the porting output location? No.** `_build_copilot_command`
(task 02.0) already emits `--allow-all-tools --deny-tool=shell --deny-tool=url` unconditionally,
regardless of the `tools` parameter's contents - this posture is shared by both the marker-research
and porting call sites (the function ignores `tools` entirely; see task 02.0's spike correction
history in `02.0-copilot-adapter/01-spike-copilot-contract.md`). `--allow-all-tools` already
covers `Write` to any path within the default path-permission scope (cwd + subdirs + system temp),
and `port_tree_headless`'s session cwd is the project root (`out_dir`/`project_root`) - the same
tree containing `.github/`, `AGENTS.md`, and `.claude/`. So every confirmed target location above
is already writable with zero additional flag work. Copilot's `write(path?)` syntax *can* scope a
grant to a specific path (`write(/path/to/.env)`), but nothing here requires exercising that,
since the existing `--allow-all-tools` posture (with `--deny-tool=shell`/`--deny-tool=url` as the
only carve-outs) already reaches the confirmed targets - a narrower `write(...)` scoping is an
optional hardening a future task could consider, not something this subtask blocks on.

**Q4. Agent vs. skill - yes, a meaningful, confirmed distinction exists,** structurally close to
Claude's own split: "agent" (`--agent <agent>` flag, `.github/agents/` directory - a custom
persona/entry-point configuration) is a genuinely separate concept from "skill" (`SKILL.md`,
reusable capability instructions, `copilot skill add/list/remove` subcommands). Neither loops nor
hooks has a clean project-level equivalent (see Q1) - the porting prompt's hint should name
concrete targets for `agents`/`skills` and leave `hooks`/`loops` to Copilot's own judgment per the
porting rules' existing "say so explicitly if you have no equivalent concept" instruction, rather
than inventing a fabricated target location for either.

**Resulting `porting_target_hint` for task 07.0 subtask 02:** a concrete sentence naming
`.github/agents/` for agents, `.github/skills/` (or `.agents/skills/`) for skills - explicitly
noting Copilot already auto-discovers `.claude/skills/` too, so re-authoring is about idiom/format
choice, not discoverability - and `.github/copilot-instructions.md`/`AGENTS.md` as the natural home
for anything that doesn't map cleanly onto a hook or loop concept, while leaving hooks/loops
explicitly named as "no fixed convention" per the porting rules' own escape hatch.
