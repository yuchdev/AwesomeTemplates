# 03 - Agentic marker research: from one-shot prompting to genuine project research

## Problem

`generate --resolve-markers` was run against a mature, well-documented project (Aegis SWR:
full `src/` tree, rich `CLAUDE.md`, `README.md`, `ARCHITECTURE.md`, docs index) and still
produced instruction-echo instead of facts:

- `agents/app-architect.md` - the "Domain model you must hold in your context" section came out
  as `> **TODO (fill in): Research this project's actual architecture ...**` even though that
  domain model is fully spelled out in the target's `CLAUDE.md` and `README.md`.
- `agents/background-reviewer.md` - the hot-paths marker resolved to a restatement
  ("Identify this project's actual performance-sensitive hot paths ... and name the concrete
  modules/files to watch here") instead of naming any module.
- `agents/feature-reviewer.md` - the untrusted-input marker resolved to
  "Identify the specific categories of untrusted or attacker-influenced input ..." instead of
  naming crash dumps, logs, and telemetry as the attacker-influenced inputs the target ingests.

## Root cause

Three compounding causes, all in `src/awesome_templates/resolver.py`:

1. **The model cannot research.** `resolve_one` is a single Messages API call. Its only
   evidence is `gather_context`'s static bundle: heads of README/CLAUDE.md/AGENTS.md, one
   dependency manifest, a bare *file-name* listing of `src`/`tests`, and ADR/spec heads.
   No source file contents, no follow-up reads, no grep. Markers that ask for
   *concrete modules/files* ("name the concrete modules/files to watch", "hot paths",
   "specific input categories") genuinely cannot be answered from file names alone, so a
   well-calibrated model correctly answers `confident=false`.
2. **The prompt rewarded refusal.** The old `_SYSTEM` led with "grounded ONLY in the project
   bundle ... never invent", which biased the model toward `confident=false` even when the
   bundle *did* carry the answer (as it did for the app-architect domain-model marker - the
   target's CLAUDE.md describes the pipeline, backend families, and data schema explicitly).
3. **The low-confidence fallback echoes the instruction verbatim.** `render()` emits
   `> **TODO (fill in): {marker.instruction}**` as the headline. So every low-confidence
   resolution *is* the instruction, reprinted - the exact symptom observed.

Causes 2 and 3 are prompt/rendering bugs, fixed now (see "Interim fixes shipped" below).
Cause 1 is architectural and is what this document proposes to fix.

## Interim fixes shipped (same commit as this doc)

- `_SYSTEM` rewritten: treat the target as a real, existing project; write declarative
  present-tense facts naming real modules/files/schemas in backticks; explicitly forbid
  restating the instruction ("this project's actual ...", "identify the ...", "once the
  codebase ..." are named as failures); `confident=true` whenever the bundle names the
  concrete things asked about; even `confident=false` output must be partial facts, never
  a restatement.
- `gather_context` now also reads `ARCHITECTURE.md` and `docs/README.md`.

These make the one-shot path much better on documentation-rich targets, but they cannot make
it *research*. Cause 1 is still open: `resolve_one` has no way to open a file it wasn't
handed in advance. The rest of this document proposes how to close that gap.

## Proposed architecture: one headless Claude Code pass over the whole marker manifest

The earlier draft of this document proposed hand-rolling a research harness: a bespoke
Messages-API tool-use loop (`read_file`/`grep`/`list_tree`) that would produce a structured
"fact sheet," consumed by a second, cheaper one-shot pass per marker. That is real,
buildable work, but it is also reinventing something that already exists and already does
this job well: `.claude/agents/create-from-template.md`, run inside a real Claude Code
session, genuinely researches a target project (`Read`/`Grep`/`Glob`, no fixed bundle) and
writes grounded prose directly into the marker's location - because it runs inside an actual
harness instead of a single stateless call. Its own module docstring already contrasts the
two: it is "the interactive, in-editor pass"; `resolve_tree` is "the programmatic ... pass."

The fix is to stop treating those as two different pieces of software with two different
research qualities, and make the programmatic path *use* the same harness the interactive
one already gets for free.

**Assumption this design makes, made explicit:** the machine running
`generate --resolve-markers` has the `claude` CLI installed and authenticated (its own
login, or `ANTHROPIC_API_KEY` - confirmed at implementation: the session inherits whatever
auth the installed CLI already has). This is a new, heavier dependency than today's `ai`
extra + `ANTHROPIC_API_KEY`, and is a deliberate trade documented below under
"Prerequisites."

```
generate --resolve-markers
        │
        ▼
  scan_tree(out_dir)                     # markers.py - unchanged, already walks every
        │                                # generated Markdown file, agents AND loops
        ▼
  marker manifest (one table: file, kind, instruction, placement)
        │
        ▼
  one headless `claude` subprocess, cwd = out_dir, tools jailed to
  Read/Grep/Glob/Edit, given the manifest + create-from-template's research method
        │                                # the model researches out_dir for real, then
        │                                # edits every listed file in place - one
        ▼                                # session, so facts learned resolving one
  out_dir, markers gone or TODO'd        # marker are already in context for the next
        │
        ▼
  scan_tree(out_dir) again → diff against the manifest → ResolveSummary
```

### The manifest: one table, every marker, every file, before any research starts

Building the manifest is the one piece of new code this needs on top of what already exists:
walk `markers.scan_tree(out_dir)` (already correct - it is the same scan `resolve_tree` calls
today, and it already covers `loops/`, not just `agents/`) and render it as a table the
prompt embeds verbatim, e.g.:

| # | File | Kind | Instruction |
|---|------|------|-------------|
| 1 | `.claude/agents/app-architect.md` | TEMPLATE-INIT | Research this project's actual domain model ... |
| 2 | `.claude/agents/background-reviewer.md` | TEMPLATE-INIT | Identify this project's actual performance-sensitive hot paths ... |
| 3 | `.claude/loops/implement-milestone.md` | TEMPLATE-INIT | list this project's own milestone exit gates ... |

Handing the model the *complete* scope of work up front, in one session, is what the user
request behind this document calls "sharing information between generated text pieces": the
domain model the model derives while answering row 1 is still in its context when it answers
row 2's hot-paths question in a different file, so the two markers can't drift into
contradicting each other the way two independent one-shot calls (today's behavior) can. This
also replaces the older draft's fact-sheet JSON artifact - the *conversation itself* is the
shared context; there is no separate schema to design, version, or keep in sync with what
markers actually ask.

### Invoking Claude Code headlessly

Roughly: `claude -p "<prompt embedding the manifest>"` with `cwd=out_dir`, restricted to
`Read`, `Grep`, `Glob`, `Edit` (no `Bash`, no `WebFetch` - nothing beyond what
`create-from-template.md`'s own `allowed-tools:` frontmatter already grants it today), and
whatever non-interactive permission mode lets it run unattended without a human approving
each tool call. **The exact flags are not pinned here on purpose** - confirm the current
CLI's headless/print-mode and permission-mode contract against `claude --help` at
implementation time rather than trusting flag names guessed in a design doc.

The prompt reuses `create-from-template.md`'s research method and hard rules (deep-analyze
the target before answering; ground every fact in something actually read; TODO rather than
fabricate on genuine low confidence; never touch anything outside the manifest's file list)
rather than re-deriving them - but see "Packaging gap" below, because that file cannot simply
be read off disk at runtime by an installed copy of `awesome-templates`.

### Result reconciliation - no self-reported summary needed

`resolve_tree` currently builds `ResolveSummary` from each call's own `confident` field. A
subprocess that edits files in place doesn't return structured JSON, so summary counts come
from a *before/after diff* instead: `scan_tree(out_dir)` once before the subprocess runs
(the manifest) and once after. A marker gone from the after-scan is `resolved`; one now
rendered as `> **TODO (fill in): ...**` is `todos`; a `SME REVIEW NEEDED` marker is always
`human_review` regardless of whether it changed, exactly as today. This is more robust than
trusting the model's own self-report, and it reuses code that already exists
(`markers.scan_tree`) instead of adding a new structured-output contract.

## Prerequisites and detection

Requiring the `claude` CLI is a real new dependency for `--resolve-markers`, on top of the
`ai` extra + `ANTHROPIC_API_KEY` the feature documents today. `resolve_tree` should detect
its absence up front (`shutil.which("claude")`) and fail with one actionable message, the
same posture the existing auth-error path already has - not a bare subprocess `FileNotFoundError`.
Root `CLAUDE.md`'s `generate --resolve-markers` documentation needs a one-line update once
this ships, so the dependency isn't a silent surprise.

**Decision (as implemented):** the older one-shot `resolve_one` path survives as an
automatic fallback when `claude` isn't on `PATH`, with a warning naming the quality trade -
so the existing documented interface (`ai` extra + `ANTHROPIC_API_KEY`, no CLI) keeps
working. The headless path itself needs neither the `ai` extra nor an explicit API key
(the CLI's own login suffices); the tutorial/test-conventions/roadmap increments still do,
and are skipped with a warning rather than failing the run when the key or extra is absent.

## Testability

A real subprocess call obviously can't run in unit tests. The existing fake-client pattern
(`make_client=` on `resolve_tree`, `tests/test_resolver.py`) has a subprocess-boundary
equivalent: point `PATH` at a tiny fake `claude` script for tests, and inject the command
used to invoke it (e.g. a `run=` parameter defaulting to `subprocess.run`) so tests can assert
on the constructed argv/prompt without executing anything. A `--dry-run` mode that prints the
manifest and the assembled prompt without invoking the CLI is also worth having independent
of tests - it makes the feature inspectable before it spends a real session.

## Scope and safety in headless mode

Interactive `create-from-template` runs with a human watching each edit land. This path runs
unattended as part of `generate`, with nothing reviewing its edits before they're on disk.
Two things this changes, both already implied above but worth stating as hard requirements
rather than nice-to-haves:

- Tool grant is a hard allowlist (`Read`, `Grep`, `Glob`, `Edit` only) - no `Bash`, no network
  tools, regardless of what the ambient `claude` install's own defaults might otherwise allow.
  The allowlist is the *only* guard, found the hard way: the CLI's permission layer blocks
  `Edit` on `.claude/**` as "sensitive files" even under `acceptEdits` and even with an
  explicit `--allowedTools "Edit(<kit>/**)"` rule - and the kit's agent/loop files all live
  under `.claude/`. The session therefore runs `--permission-mode bypassPermissions`, and the
  security posture rests entirely on the tool allowlist plus the closed file set below.
- The prompt states the manifest's file list as a closed set the session may edit - not "scan
  for markers yourself," even though the model could rediscover them by grepping. Handing it
  the closed list and forbidding edits outside it removes a whole class of unattended
  scope-creep that isn't a concern in the supervised, interactive usage.

## Other improvements to fold in

- **Packaging gap.** `.claude/agents/create-from-template.md` is this *repo's own* maintainer
  tooling - per root `CLAUDE.md` it is "deliberately not shipped inside `templates/<preset>/`."
  A `pip install`ed `awesome-templates` has no clone of this repo on disk, so `resolver.py`
  cannot read that file by path at runtime. Re-embed the research method and hard rules as a
  prompt string owned by `resolver.py` (the same way `_SYSTEM` is a string today), not a
  runtime read of the agent file - this also avoids two copies of the same instructions
  silently drifting apart. The tradeoff: the interactive agent and the headless prompt become
  two things a change to one won't automatically keep in sync; call this out in
  `create-from-template.md`'s own "second, programmatic resolver" note when it's updated.
- **Loops, not just agents.** `create-from-template` is deliberately agents-only ("Only edit
  `<target>/.claude/agents/*.md`"). The manifest-driven prompt must *not* inherit that scope
  restriction - `markers.scan_tree` (and today's shipped `resolve_tree`) already resolves
  `loops/` markers too (`implement-milestone.md`, `implement-subtasks.md` both carry them),
  and the manifest table is what keeps that scope correct automatically, since it's built
  from the real scan rather than a hardcoded glob.
- **CLI version drift.** Pinning behavior to specific `claude` CLI flags is fragile across
  CLI versions. Worth a `claude --version` check with a clear "unsupported CLI version"
  failure rather than an opaque flag-parsing error from the subprocess.
- **Non-interactive/CI environments.** `generate` is meant to be runnable in automated
  pipelines, not just by a human at a keyboard. Confirm the headless CLI's non-interactive
  contract actually works without a TTY (CI runners, no `stdin`) before relying on it here -
  this is a different concern from "detect it's installed."
- **This is likely both cheaper and better than what's shipped**, not just architecturally
  cleaner: today's `resolve_tree` makes one Messages API call *per marker*. One headless
  session covering the whole manifest replaces N one-shot round trips with one, on top of
  the quality improvement from giving the model real read access - worth stating as a
  concrete benefit, not just a nicer design.
- **Same treatment for the other three AI increments.** `maybe_write_tutorial`,
  `maybe_describe_test_conventions`, and `seed_first_milestone`/`propose_first_milestone` are
  all still one-shot Messages-API calls against the same thin `gather_context` bundle this
  document diagnoses as insufficient for markers. They are out of scope for this document
  (their outputs are more forgiving of a thinner bundle - a tutorial or a milestone proposal
  tolerates vagueness in a way a marker claiming a concrete module path does not), but the
  same "let Claude Code actually read the project" upgrade would plausibly help all three.
  Flagged here as a follow-up, not scope creep into this document.

## Rollout

1. `manifest.py` (or a function in `resolver.py`): render `scan_tree`'s output as the
   embedded table; unit-testable with no subprocess involved (pure function of markers).
2. Prompt module: the re-embedded research method + hard rules (see "Packaging gap" above),
   parameterized by the manifest table.
3. Subprocess invocation with an injectable `run=`; `shutil.which("claude")` pre-check;
   `--dry-run` support.
4. Result reconciliation: before/after `scan_tree` diff → `ResolveSummary`, replacing the
   per-call `confident` bookkeeping `resolve_one` uses today.
5. Fake-`claude`-on-`PATH` test harness; unit tests for manifest rendering, prompt assembly,
   and reconciliation logic independent of any real subprocess.
6. Update root `CLAUDE.md`'s `generate --resolve-markers` docs and
   `create-from-template.md`'s "second, programmatic resolver" note for the new prerequisite
   and the loops-scope difference.
7. Integration test: run the full pass against a documentation-rich fixture repo (with a real
   `claude` CLI available in that environment) and assert the three originally-failing
   markers resolve to prose containing concrete module paths and zero instruction-echo.

## Acceptance criteria

Running `generate --resolve-markers` against a mature target (Aegis SWR as the reference):

- `app-architect.md` gains a real "Domain model" section naming the target's actual
  subsystems, schemas, and entry points with correct file paths.
- `background-reviewer.md`'s hot-paths sentence names concrete modules and says why each is
  performance-sensitive.
- `feature-reviewer.md` names the target's actual untrusted input categories and where they
  are ingested.
- Zero resolved markers contain the phrases "this project's actual", "identify the", or a
  restatement of their instruction.
- A rerun on the same target is a no-op: `scan_tree` finds zero markers, and the run skips
  invoking the `claude` subprocess entirely rather than spending a session to confirm nothing
  changed.

## Deferred: the in-house tool-loop / API-based alternative

An earlier draft of this document proposed a hand-rolled Messages-API research harness
(`read_file`/`grep`/`list_tree` tools, a structured fact-sheet artifact, a second one-shot
resolution pass) as an alternative to depending on the `claude` CLI. That design is real and
may still be worth building - e.g. if the `claude`-CLI dependency this document now assumes
turns out to be unacceptable for some deployment of `generate` - but it is not what ships
first. It has been moved, content intact, to its own milestone:
[`0002-api-based-marker-research/plan.md`](../0002-api-based-marker-research/plan.md).
